# Design by Contract: Operational Rules

Extracted from Bertrand Meyer's *Object-Oriented Software Construction* (Ch. 11, Ch. 12, §16.1, §23.6). Restated language-neutrally — no Eiffel syntax.

## 1. The contract metaphor: obligations and benefits on both sides

**Trigger**: Writing any function/method boundary that will be called by code you don't control (a library function, a public method, an internal API between modules).

**What goes wrong without it**: Without an explicit split of responsibility, every routine either trusts blindly (and breaks on bad input) or checks everything (and drowns in redundant validation code that duplicates what the caller already knows). Teams argue forever about "should this function validate its arguments" because there's no agreed rule for *whose job it is*.

**What to do**: Treat every function signature as a two-sided contract, not a one-sided demand. A precondition is what the caller promises to have arranged before calling; a postcondition is what the function promises to have achieved by the time it returns. Crucially, reframe what "benefit" and "obligation" mean: the precondition is an *obligation for the caller* but a *benefit for the function* — it narrows the set of situations the function must handle. Symmetrically, the postcondition is an *obligation for the function* but a *benefit for the caller* — it's the guarantee the caller gets to build on without re-deriving it. A strong precondition makes the supplier's job easier (fewer cases to handle); a strong postcondition makes the caller's job easier (more to rely on). Good interface design is negotiating the best trade of these two, not maximizing either one unilaterally.

**How to check**: In a diff, look for a new or changed function signature. Ask: is it documented (in a comment, a type, or an assertion) what the caller must arrange, and what the function guarantees in return? If a reviewer has to read the function body to know what's safe to pass in, the contract isn't stated — it's implicit, and implicit contracts get violated silently.

## 2. Preconditions: what belongs in one, and who checks it

**Trigger**: Deciding whether an argument, an object's state, or an ordering constraint needs to be checked before a function runs — e.g., "can `index` be out of range," "can the collection be empty," "must `connect()` have been called first."

**What goes wrong without it**: Two failure modes. Either the constraint is nowhere (undocumented, unchecked) and the function corrupts state or produces garbage on bad input with no diagnosis; or the constraint is checked in *both* the caller and the callee, which superficially looks safer but is strictly worse — it's a second copy of logic that will drift, and it hides the real question ("whose bug is this?") behind a defensive `if`.

**What to do**: For every consistency condition a routine needs, assign responsibility to exactly one side — the caller (as a precondition) or the routine itself (as an internal branch it handles as a normal case, not an error). This is a design choice, not automatic; Meyer calls the caller-responsible style "demanding" and the routine-responsible style "tolerant." Prefer the demanding style for routine-to-routine (software-to-software) contracts, especially in reusable code: a routine that tries to be tolerant of every abuse ends up doing three jobs (its actual job, guessing what abnormal input "means," and reporting that guess) and does none of them well. A precondition is only legitimate if you can justify it purely from the specification of what the function does — not from "this makes my implementation easier" (a precondition that only exists to protect one implementation choice from its own limitations should be described in terms of what the function *promises*, not how it's built). And a precondition may only reference things the caller can actually observe — never a hidden/private detail the caller has no way to check in advance.

**How to check**: For every new guard clause / assertion / argument check in a diff, ask: (a) is it phrased in terms of the public contract, not an implementation accident? (b) does the caller have access to everything needed to satisfy it before calling? (c) is there a *second* check for the same condition somewhere else in the call chain (in the caller, or defensively re-checked inside the callee after the caller already validated it)? Duplicate checks for the same condition are a code smell, not extra safety.

## 3. The Non-Redundancy argument: why a routine should not re-check its own precondition

**Trigger**: You're about to add a defensive `if` inside a function body that re-tests something already stated (or implied) as a precondition — "just in case."

**What goes wrong without it**: This looks harmless locally — "an extra check never hurts" — but Meyer's argument is that this reasoning only holds if you look at one routine in isolation. At the scale of a real system with thousands of call sites, every redundant check is itself new code, with its own potential for bugs, that needs its own justification and maintenance, and that duplicates a condition already guaranteed elsewhere. Multiply this by every routine and you get a system where reliability is chased by adding more code, which needs more checks, forever — and the underlying cause of unreliability (a fuzzy, unstated division of responsibility) is never fixed. Software also does not "wear out" or suffer transmission noise the way hardware signals do, so the hardware argument for redundant checking (sender and receiver both verify a signal) doesn't transfer to software-to-software calls.

**What to do**: Once you've decided a condition is the caller's responsibility (stated as a precondition), the callee must *not* re-test it. This isn't a suggestion — it's the whole point of assigning responsibility in the first place. If a precondition violation happens at runtime, that is unambiguously a bug in the caller, and the callee's job is done: it "may do what it pleases" because the contract wasn't honored, so there's no case to handle. If you don't trust an untrusted or unverified caller, that's a signal the condition belongs on the callee side (or that you're not actually in a software-to-software contract — see section 6), not a signal to check twice. This is a Zen-sounding but concrete rule: reliability comes from checking less, redundantly, and specifying more, precisely.

**How to check**: Grep the routine body for a condition that also appears in its documented precondition/guard clause. If found, one of the two is dead weight and should be deleted — usually the internal one, unless you've deliberately decided the condition moves to the callee's responsibility (in which case the caller-side check should go, and the "precondition" claim in the docs should be removed too, since it's no longer true).

## 4. Postconditions: what the supplier guarantees, and why writing them changes usage

**Trigger**: Writing (or reviewing) a function that returns a value or mutates state, especially a public one other code will depend on.

**What goes wrong without it**: Callers reverse-engineer behavior from reading the implementation or from trial and error, because "what does this actually guarantee" was never written down as something distinct from "what does it currently do." This means the *implementation* becomes the spec by default — any refactor that preserves behavior a caller depended on but wasn't promised is a legal, silent breaking change, because nothing said the old behavior was a promise.

**What to do**: State the postcondition as a property of the return/output relative to the input and the object's prior state — independent of *how* the function computes it. This is the difference between an instruction ("assign `count + 1` to `count`") and an assertion ("on return, `count` equals its value on entry plus one") — the former is *how*, the latter is *what*, and only the latter is a promise a caller can build on across refactors. Once a postcondition is written down this way, it does double duty: it's the correctness target for the implementer, and it's the *only* part of the implementation a caller is allowed to depend on. Anything true of the current implementation but not stated in the postcondition is an implementation detail, not a guarantee, and callers relying on it are relying on something you never promised.

**How to check**: For a new/changed public function, look for a docstring, type signature, or comment that states outcomes in terms of before/after values — not a paraphrase of the code. If the only "documentation" is the function body itself, there's no postcondition, just an accident that happens to be observable.

## 5. Class invariants: what must hold between operations, not during them

**Trigger**: A type/class has two or more fields whose values must stay consistent with each other (a count and a backing array's size, a cached total and the list it summarizes, a "connected" flag and a live socket).

**What goes wrong without it**: Consistency rules end up scattered — half-enforced in the constructor, half-enforced in one mutator, forgotten in a new mutator added six months later. Because there's no single place the rule is declared, nobody notices when a new method breaks it, and bugs show up far from their cause (the object was already inconsistent for several calls before something finally read the broken field).

**What to do**: Write the consistency rule once, as an invariant of the type, understood to hold at every point the object is *observable from outside* — after construction, and before/after every externally-visible method call — but explicitly **not** required to hold in the middle of a method's execution. A method is allowed to temporarily break the invariant while it works toward its goal, as long as it restores the invariant before returning control to the caller. This distinction matters because it's what makes invariants practical: if they had to hold at every single statement, you could never write a method that touches more than one field. The invariant is effectively "anded into" both the precondition and postcondition of every public method (giving the implementer the benefit of assuming it on entry, and the obligation of restoring it on exit) — but keeping it as one separate, named statement (rather than copy-pasted into every method) is what lets it double as documentation of "what this class is actually about," and lets it apply automatically to methods added later.

**How to check**: For a class/struct with multiple related fields, look for the rule connecting them stated in exactly one place (a `check_invariant`-style method, a property test, a comment at the type level) rather than re-derived per method. Then check every new public method: does it leave the object in a state where that rule holds, even if it was violated mid-method? A field mutated in one method without its dependent field being updated in the same method is the classic violation.

## 6. Contracts and inheritance: weaken preconditions, strengthen postconditions — never the reverse

**Trigger**: Subclassing, implementing an interface, or overriding/redefining a method that has a contract on the base type.

**What goes wrong without it**: This is where contract violations become invisible at the call site. A caller holding a reference typed as the base class calls a method through it; at runtime, thanks to polymorphism, the actual object may be an instance of a subclass with a *redefined* version of that method. The caller's code was written against the base type's contract and has no idea a subclass is involved. If the subclass's override demands *more* than the base contract did (a stronger precondition), a call that was legal under the base contract can now fail at runtime through no fault of the caller. If the override promises *less* (a weaker postcondition), the caller may proceed on an assumption that no longer holds. Either way, the caller was honest and still got cheated — which is exactly the scenario substitutability is supposed to prevent. (This is the same idea usually cited today as the Liskov Substitution Principle; Meyer derives it independently from the contract metaphor and calls it subcontracting.)

**What to do**: A redefined/overriding method may only replace the precondition with one *equal or weaker* (accept everything the original accepted, plus optionally more), and the postcondition with one *equal or stronger* (guarantee everything the original guaranteed, plus optionally more). Never the reverse. Concretely: a subclass override should be implemented as "original precondition OR new condition" and "original postcondition AND new condition" — not as a wholesale replacement — so it's structurally impossible to accidentally narrow what's accepted or weaken what's promised. Invariants only ever add: every ancestor's invariant applies to the descendant too, in addition to (not instead of) the descendant's own. One practical wrinkle: if a subclass genuinely needs a real-world-justified narrower precondition (e.g., a bounded stack's `push` really can fail when full, but a general stack's can't), don't hardcode the narrower rule as a literal strengthening — instead, expose the constraining condition as an overridable query on the base type itself (e.g., a `full` check that the base type defines as always false, and the bounded subclass redefines to reflect real capacity). Then the *documented* precondition ("not full") never changes text across the hierarchy, even though its concrete meaning specializes per subclass — so callers coded against the abstract precondition remain correct for every subclass.

**How to check**: For any override/redefinition, diff the new precondition against the parent's: is every case the parent accepted still accepted (weaker-or-equal), or could some previously-legal call now fail? Diff the new postcondition against the parent's: does the override still guarantee everything the parent promised, or has some guarantee been dropped or hedged (weaker-or-equal in the wrong direction)? Also check: does the override rely on state or behavior invisible from the base type's public interface? If a caller holding the base type could never observe the difference, it's probably fine; if it could be surprised, it's a substitutability violation.

## 7. Contracts vs. defensive programming: the argument and its real limits

**Trigger**: Deciding, system-wide, how paranoid to be about checking assumptions — not just at one function, but as a policy.

**What goes wrong without it**: Teams often adopt "defensive programming" (check everything, everywhere, just in case) as a blanket policy, believing more checks can only help. Meyer's counter is that this treats reliability as a local, per-function property, when it's actually a systemic one: redundant checks are extra code, extra code has its own bugs and its own maintenance cost, and — critically — they let developers stop asking the harder question of *whose responsibility a condition really is*, which is the question that actually produces reliable systems.

**What to do**: Default to assigning each condition to exactly one owner (section 2–3) rather than checking everywhere. But recognize the discipline's real limits, which Meyer states explicitly rather than glossing over: (a) sometimes checking a precondition in advance costs almost as much as doing the operation itself (e.g., you can't cheaply know in advance whether a matrix is invertible without doing most of the work of inverting it) — here, checking upfront is wasteful, so the practical move is to attempt the operation and check the *outcome* afterward (an "a posteriori" scheme) rather than gate it beforehand; (b) some conditions genuinely can't be expressed in a simple assertion language (global structural properties like "this graph has no cycles"); (c) some conditions depend on the outside world (a user, a network, a device) and can't be verified except by attempting the operation and seeing what happens. In all three cases, defensive-style "try and detect failure" is not a violation of the discipline — it's the discipline correctly recognizing that a precondition-based (a priori) contract isn't always the cheapest or even the only way to express "whose responsibility is this."

**How to check**: When you see a check that looks defensive/redundant, don't reflexively delete it — first classify why it's there. If it's guarding a condition that's genuinely expensive or impossible to verify in advance (matches a/b/c above), it's a legitimate a posteriori check and should be documented as such. If it's cheaply re-verifying something the caller already promised and could have checked, it's true redundancy and should go.

## 8. What contracts are not: input validation and control structures

**Trigger**: Writing a function that reads data from a user, a network socket, a file, sensor input, or any other source outside your own codebase's control.

**What goes wrong without it**: Treating a precondition as if it could sanitize untrusted input is a category error — assertions describe a contract *between two pieces of software you both control*; they say nothing to a human typing at a prompt or a malformed payload arriving over a wire, and a "precondition" of the form "input is well-formed" on a function that reads raw external input is wishful thinking dressed as a check, not a reliability mechanism. Confusing the two also tempts developers to use assertions as `if/else` case-dispatch ("handle case A vs. case B") — but a precondition violation isn't supposed to be a normal branch a routine plans for; it's supposed to be understood as a bug when it happens.

**What to do**: Keep contracts strictly at software-to-software boundaries. For anything crossing from the outside world into your system, put a dedicated filtering/validation layer at the edge — its whole job is to accept messy external input and either reject it or convert it into a form that *does* satisfy the internal preconditions of your processing code, which can then stay simple and demanding. Downstream of the filter, contracts resume as normal. Separately: don't reach for assertions to implement ordinary case handling; use normal conditionals for expected, planned-for cases, and reserve preconditions/postconditions/invariants for statements of what should always be true given correct usage.

**How to check**: Trace where a precondition-guarded value comes from. If it originates from user input, network payload, file contents, or any other external source with no filtering step in between, that's a red flag — either add a validation layer before the boundary, or reclassify the "precondition" honestly as a runtime check with real error handling, not a contract. Also worth noting explicitly for this material's stated purpose: a contract is not a substitute for testing. A contract states what should be true; a test is independent evidence that the implementation actually achieves it under real conditions (including the malformed, adversarial, and boundary cases a spec alone won't surface). Contracts make testing more productive — a violated assertion turns a silent wrong-answer bug into an immediate, localized failure with a clear "which side broke this" diagnosis — but they don't remove the need to write and run tests.

## 9. Exception handling as contract violation: retry or fail, not "handle and continue"

**Trigger**: Writing a `catch`/`rescue`/`except` block, or any error-recovery path, for a call that might fail.

**What goes wrong without it**: The common failure pattern (well-documented across languages, not just old ones) is an error handler that prints or logs something, then returns *as if the routine succeeded* — silently lying to the caller. The caller proceeds on the assumption the postcondition holds; it doesn't; the real failure surfaces much later, far from its cause, as corrupted state or a wrong answer nobody can trace back. This is functionally indistinguishable from `goto`-based control flow crossing module boundaries, and it's exactly the failure mode Meyer traces to the fatal Ariane 5 bug: an exception path that was reasoned about informally rather than treated as part of the contract.

**What to do**: A failure handler has exactly two honest options, and no others. (1) **Retry**: change something about the conditions that caused the failure (state, input, strategy, or simply wait out a transient external condition) and attempt the *original* operation again from the start — if this eventually succeeds, the caller is never aware anything went wrong, because the contract *was* ultimately fulfilled. (2) **Fail cleanly** ("organized panic"): give up, restore the object to a state that satisfies its invariant (even though the postcondition won't be met), and propagate the failure to the caller so *it* can decide what to do — never swallow the failure and return normal-looking output. What a handler must never do is exit through the error path while pretending the postcondition was satisfied. A narrow exception exists for genuine **false alarms** — e.g., a spurious OS signal that's known to be harmless — where resuming exactly where you were is legitimate; but this only applies to a small class of external-signal cases, never to assertion violations, and even then it's usually better to prevent the spurious signal from being raised at all than to catch and ignore it routine by routine.

**How to check**: For every catch/rescue block in a diff, trace what happens after it: does execution definitely end in either (a) a fresh attempt at the original operation (retry) or (b) a propagated error/exception plus a state that still satisfies the object's invariant (clean failure)? If a catch block ends by returning a default value, logging and continuing, or falling through to subsequent code as though nothing happened — while the operation's actual postcondition was never achieved — that is the anti-pattern to flag. Also check: does the handler leave the object in a state satisfying its invariant before propagating, even if the postcondition can't be met? An error path that leaves invariant-violating state behind is worse than one that fails loudly, because the corruption will resurface as a *different*, harder-to-diagnose bug later.

## Where does this belong?

Honestly: **it should not be one monolithic new skill.** Design by Contract is really three separable disciplines wearing one name, and each one has a natural, better-fitting home.

**Extend `decomposition`** with the interface-contract material: sections 1–3, 5, and 8 (contract metaphor, precondition ownership/demanding-vs-tolerant design, class invariants, and "not input validation"). `decomposition` already asks "what should this boundary hide, and what does its interface promise?" — preconditions and postconditions *are* the answer to "what does this interface promise," stated formally instead of vaguely. The Non-Redundancy argument in particular belongs here as a direct extension of "premature generality / defensive scaffolding costs more than duplication": redundant validation checks are a specific instance of that broader anti-pattern, not a separate concern. Class invariants belong here too — they're the formal version of "what must this module keep true about its own internal state," which is exactly the kind of boundary question `decomposition` already covers.

**Extend `unit-testing`** with sections 4, 7, and the last paragraph of section 8: postconditions as the *thing tests should assert*, not implementation details; the "contracts complement tests, they don't replace them" caveat; and the a priori/a posteriori distinction as a design pattern that shows up directly in test design (should you assert preconditions before calling, or call and assert on the outcome?). `unit-testing` already draws the line between observable behavior and implementation details — a postcondition, properly written, *is* the observable-behavior half of that line, phrased as a contract instead of as a test assertion. This is a natural, concrete place to teach "write the postcondition first, then the test is just an executable instance of it."

**A genuinely new, standalone `design-by-contract` skill is warranted for exactly one thing: sections 6 and 9** — inheritance/substitutability rules and the retry-or-fail exception discipline. These don't fit cleanly into either existing skill: they're not about where a boundary goes (decomposition) or about test design (unit-testing); they're about a specific, easy-to-violate-invisibly correctness property that only shows up when polymorphism or error recovery is involved, and it needs its own trigger conditions ("you're overriding a method," "you're writing a catch block") independent of whichever skill someone happened to reach for. This narrower skill can then *reference* the interface-contract vocabulary established in `decomposition` (precondition/postcondition/invariant) rather than re-deriving it, keeping the three pieces consistent without duplicating the whole theory in three places.
