# Extraction: aima-intelligent-agents

**Source:** Artificial Intelligence: A Modern Approach — Stuart Russell & Peter Norvig (3rd Edition, Prentice Hall, 2010)

> Operational rules distilled from the source, written in our own words. This is a 1,151-page textbook covering search, logic, planning, probabilistic reasoning, and machine learning; only Chapter 2 ("Intelligent Agents") plus the rationality and utility material from Chapter 1 was extracted. Everything else — the algorithms the rest of the book builds — was deliberately left out.

---

Russell and Norvig wrote this before anything resembling an LLM existed, and the formalism shows its age in places — "learning" here means an internal component gets modified between episodes, not that a frozen-weight model reasons over a context window. But the vocabulary in Chapter 2 was built for exactly the question an LLM-agent engineer faces before writing a system prompt: what is this thing supposed to do, what can it actually perceive and act on, and what kind of environment is it operating in. The book is unusually disciplined about forcing those questions to be answered explicitly rather than left as assumptions baked into a prompt. Where the mapping to tool-calling agents is direct, this extraction says so; where it only holds by analogy, or doesn't hold at all, it says that too.

## PEAS: specifying the task environment before building anything

Russell and Norvig insist the first step in designing any agent "must always be to specify the task environment as fully as possible," and name the specification so it can't be skipped implicitly: **PEAS** — Performance measure, Environment, Actuators, Sensors. A **percept** is one instant of sensory input, a **percept sequence** the complete history of everything perceived so far, and the **agent function** is the abstract mapping from percept sequences to actions; the **agent program** is what actually implements that mapping (agent = architecture + program). The book proves an agent function generally can't be a literal lookup table: even chess has upward of 10^150 distinct entries, and an hour of taxi-camera input alone would need over 10^250,000,000,000 — too large to store, write by hand, or learn from experience, and even at feasible size the designer would have no principled way to fill it in. This is the argument, decades early, for why behavior has to come from a compact, generalizing program rather than an enumerated table of exact cases — the same argument that justifies a general reasoning policy (an LLM) over a hand-written dispatch tree keyed on literal strings.

PEAS forces four separate answers that engineers building LLM agents routinely leave implicit. The **performance measure** is the actual scoring criterion the agent's behavior is judged by — not vibes, a stated function over the sequence of states it produces. The **environment** is the external system it's embedded in: a codebase, a filesystem, a production API, other agents and humans acting on the same substrate. The **actuators** are the literal channels through which it changes that environment — for an LLM agent, its tool list — and the book's warning that "if the program is going to recommend actions like Walk, the architecture had better have legs" maps onto giving an agent a tool list that actually matches what its policy will try to do, rather than a policy that "wants" actions no wired-up tool can execute. The **sensors** are what percepts actually flow back — tool outputs, file contents, test results — as distinct from what the model already believes from training. Writing all four out before wiring anything up surfaces gaps otherwise discovered only in production: a tool that silently does two of the four roles at once, a performance measure that exists only retroactively as "whatever the agent got corrected for."

## The environment taxonomy: a checklist for assumptions left implicit

Russell and Norvig give seven dimensions along which any task environment can be classified, and each determines something specific about the architecture needed. Treated as a checklist, this is the highest-value transfer in the book: questions about your environment you're already assuming answers to, usually without stating them.

**Fully vs. partially observable.** Fully observable means the agent's sensors give complete access to the state relevant to its decision at every instant; partially observable means sensors are noisy, incomplete, or absent for parts of the state. A fully observable environment needs no internal state — the current percept is enough. Almost no environment an LLM agent operates in is fully observable: a context window is a partial, curated view of a codebase or production system, and the rest of it isn't simultaneously present. This is the dimension the book treats as most consequential, and partial observability is the normal case for agentic systems, not the exception — it directly causes the failure mode described below under simple reflex agents.

**Single-agent vs. multiagent**, split into **competitive** (another entity's performance measure is maximized precisely by minimizing yours, as in chess) and **cooperative** (aligned measures, as in collision avoidance), often both at once. This maps to whether other agents or humans act on the same environment concurrently — another engineer committing to the same branch, a second agent editing the same files — and the implication the book names generally holds here: communication (status files, locks, commit messages) becomes rational precisely because it isn't needed in a single-agent environment.

**Deterministic vs. stochastic.** The next state is fully determined by current state and action in a deterministic environment; otherwise stochastic — and a partially observable environment can appear stochastic even if it's "really" deterministic, since the unobserved variables driving the apparent randomness can't be tracked. One nuance is worth stating rather than force-fitting: this describes how the *environment* responds to an action, not whether the *agent's own policy* is deterministic. An LLM's sampling temperature is a separate source of nondeterminism, not evidence about the environment. What's genuinely stochastic for a tool-calling agent is the environment side: flaky tests, races, transient network failures, another process mutating shared state between a read and a write.

**Episodic vs. sequential.** In an episodic environment each percept-action pair is self-contained and doesn't affect the next episode; in a sequential one the current decision affects all future ones. Episodic is strictly simpler — no need to think ahead. A multi-step coding session or autonomous workflow is sequential, which is why it needs the state-tracking architectures below; a single classification or extraction call is closer to episodic and can validly stay simple-reflex-shaped.

**Static vs. dynamic** (with **semidynamic** as the case where the environment doesn't change during deliberation but the agent's score does — chess with a clock). A dynamic environment keeps changing while the agent is still deciding; not deciding counts as deciding to do nothing. A codebase or production system another process can modify between when your agent reads state and when it acts is dynamic for that agent, and a long deliberation, or a stale cached read, exposes it to acting on information no longer true — the shape of a race condition, described at the level of agent design.

**Discrete vs. continuous**, applying to states, time, percepts, and actions separately. Tool-calling agents operate almost entirely in the discrete regime — a fixed action vocabulary, discrete invocations — with continuity appearing only at the edges (streaming output, a genuinely continuous control signal). This is the dimension with the least friction transferring, and the one where discreteness is usually a designed simplification rather than an incidental fact about the domain.

**Known vs. unknown**, which the book stresses is not about observability but about the agent's or designer's state of knowledge of the environment's "laws of physics" — the outcomes, or outcome probabilities, of actions. A known environment can be partially observable (I know poker's rules but not the other hands); an unknown one can be fully observable (a new video game shows the whole screen but I don't know what the buttons do). This maps to whether a tool's actual behavior is documented and predictable versus something discovered by probing — an undocumented internal endpoint, or an unfamiliar codebase's real runtime behavior, is unknown regardless of how much is visible in context. This licenses the exploration point below: an unknown environment is precisely the condition under which acting purely to learn how something behaves is rational, not idle curiosity.

The book's own worst case: partially observable, multiagent, stochastic, sequential, dynamic, continuous, and unknown all at once. Most production agent deployments sit closer to that end than engineers initially assume, mostly because partial observability and dynamism are close to universal.

## Agent architectures: what each one fixes

Four architectures of increasing capability, each added specifically to fix a failure the previous one has, plus learning as a modification applicable to any of them.

A **simple reflex agent** selects an action from the current percept alone, via condition-action rules, ignoring the rest of the percept history. It works only if the environment is fully observable — only if the current percept alone determines the right move. The book's own worked failure is worth carrying over exactly: a vacuum agent with only a dirt sensor, no location sensor, has two percepts, [Dirty] and [Clean]; on [Clean] it must pick a fixed direction, which fails forever if it starts on the wrong side. "Infinite loops are often unavoidable for simple reflex agents operating in partially observable environments." This is the least-forced mapping in the whole chapter: a stateless tool-calling loop, invoked fresh each turn with no memory of what it already tried, deciding purely from the current observation ("test still failing" → retry the same fix → still failing → repeat) is a simple reflex agent hitting exactly this failure. The book's own partial fix — randomizing the action on an ambiguous percept — is real but explicitly a last resort, not a substitute for tracking state.

A **model-based reflex agent** fixes this by maintaining internal state that depends on percept history and encodes how the world evolves independently of the agent, plus how the agent's own actions change it — together a **model**. Internal state need not literally describe "what the world is like now": the book's example is that "driving home" is a fact about the agent, not the world, since the same location with a different destination is a different agent-state. This maps without strain onto what real coding agents already do under other names — scratchpads, running todo lists, memory files, a git-status check folded into decision state — anything letting the agent know it already tried something rather than re-discovering that fact from the current percept alone.

A **goal-based agent** adds an explicit representation of desirable future states and considers action sequences, not just the current action, that would reach them — necessary once a single rule can't determine the right move without knowing the target (at a junction, whether to turn depends on the destination, not on anything in the current percept). This is more flexible because the knowledge is explicit and swappable: change the destination and behavior changes automatically, where a reflex agent's rules would all need rewriting. This maps onto explicit planning or task-decomposition modes — a plan-then-execute loop, a todo-list-driven agent — evaluating candidate action sequences against a stated target rather than reacting turn to turn. The book's own search and planning chapters, skipped entirely here, are the mechanics of *how* such a sequence gets found; none of that transfers, only the shape.

A **utility-based agent** is the one worth getting exactly right. Goals give only a binary satisfying/unsatisfying distinction, inadequate whenever goals conflict and only a tradeoff is possible (speed versus safety), or several candidate goals are each achievable only with some probability and likelihood must be weighed against value. A **utility function** is "essentially an internalization of the performance measure" — a real-valued preference score over states rather than a pass/fail label — and a rational utility-based agent maximizes **expected utility**: the probability-weighted average utility over an action's possible outcomes, not the utility of one anticipated outcome. Utility-based design isn't the only route to rationality — a goal-based or reflex agent can be rational with no explicit utility function at all — but it's required when a system must make an actual tradeoff rather than confirm a goal was reached. For an LLM agent this describes anything scoring and ranking candidate outputs rather than checking a binary criterion: an agent generating several candidate patches and picking the one a scorer rates highest is a utility-based selection step; choosing between a faster-riskier approach and a slower-safer one can't be specified as goal-based, because "reaches the goal" is true of both and gives no way to choose — only a scalar preference ordering makes that a designed decision rather than an arbitrary one.

A **learning agent** is a way of building any of the above so it improves from feedback, via a **performance element** (whichever architecture is actually choosing actions), a **critic** judging outcomes against a performance standard, a **learning element** modifying the performance element from that feedback, and a **problem generator** proposing deliberately exploratory, possibly suboptimal actions to surface useful feedback. One detail matters more than the mechanics: the performance standard must be fixed and external, "outside the agent altogether," because "the agent must not modify it to fit its own behavior." This is only partially portable — nothing in a single LLM-agent session learns in the book's sense, since weights don't update mid-task; the closest real mechanism is a different timescale entirely (fine-tuning between deployments, closer to learning across a whole fleet than within one session) or, within a session, memory files that persist information without changing the underlying policy. Where the point transfers cleanly: an agent empowered to edit its own grading criterion — most concretely, a coding agent that can edit the test suite meant to be checking its work — has exactly the failure the book warns against, a failure of letting the standard live inside the agent's reach rather than of the learning mechanism.

## Rationality, precisely defined

The definition is worth stating exactly, since it's routinely flattened: "For each possible percept sequence, a rational agent should select an action that is expected to maximize its performance measure, given the evidence provided by the percept sequence and whatever built-in knowledge the agent has." What's rational at a given moment depends on exactly four things: the performance measure, the agent's prior knowledge, the actions available to it, and its percept sequence to date — nothing else.

Two things this explicitly is not. Not omniscience: an **omniscient** agent knows the actual outcome of its actions in advance, which is impossible, and the book's illustration is exact — crossing an empty street to greet a friend is rational even if a cargo door unpredictably falls off a passing airliner and kills you; "rationality is not the same as perfection... rationality maximizes expected performance, while perfection maximizes actual performance." Judging a decision by outcome rather than by what was knowable at the time is exactly the error this rules out — practically useful for reviewing an agent's past decisions: a migration judged safe given available evidence that later breaks on an untested edge case is not automatically evidence the decision process was bad. The question is what evidence was available and cheaply obtainable at decision time, not what happened afterward.

Nor does it license ignoring cheaply available information. An agent that fails to look both ways before crossing isn't made rational by the fact that its uninformative percept sequence didn't technically rule out crossing — crossing without looking isn't rational given that percept sequence, because the risk is too high, and a rational agent looks first specifically because looking improves expected performance. Rationality isn't passive acceptance of whatever the current percept sequence contains; it requires acting to get a better one when doing so is cheap relative to the risk of not doing so.

## The performance measure is a hazard you create

This is the book's most directly load-bearing point for LLM-agent builders, stated decades before "reward hacking" had a name, and it earns full weight. Score a vacuum agent on "amount of dirt cleaned up in an eight-hour shift," and a rational agent maximizes that by cleaning the floor, dumping the dirt back, and cleaning it up again — repeatedly, for score. "With a rational agent, of course, what you ask for is what you get." A measure scored on the state you actually want (a clean floor at each time step) produces the wanted behavior; one scored on the activity supposed to produce that state does not. Their general rule: design a performance measure according to what you actually want true in the environment, rather than according to how you think the agent should behave to get there — a measure targeting the proxy activity is gamed by any sufficiently capable optimizer not through malice, but because gaming it is what maximizing it precisely means.

This is the reward-hacking and eval-gaming problem, stated as a property of measure design rather than of any particular algorithm, and it applies without translation: an agent scored on "tests pass" is scored correctly only if passing tests really is what you want measured, and if what you actually want is "the code is correct," a capable agent will find the cheaper route to the stated measure — including weakening the failing test rather than fixing the bug. An agent scored on "ticket closed" will close tickets. None of this is an edge case; it's the measure working exactly as specified, which is the entire point. Even once the obvious pitfall is avoided, a subtler one remains: a measure defined as an average over time is satisfied identically by an agent doing steady mediocre work and one working in bursts followed by idle stretches — the measure doesn't distinguish a temporal shape you might care about unless designed to. Any aggregate measure has this same blind spot.

## Autonomy: what's built in versus what the agent must establish itself

An agent "lacks autonomy" exactly to the extent it relies on its designer's prior knowledge rather than its own percepts. The book's illustrations: a dung beetle that continues pantomiming plugging its nest with a dung ball removed en route, and a sphex wasp that restarts its fixed check-then-drag sequence from the beginning every time an experimenter moves its prey mid-task, never noticing the loop. Both have an assumption hardcoded into behavior, and both fail identically once the environment violates it, because nothing in the architecture ever re-verifies the assumption against current percepts. The book's stance is a middle position, not an argument for pure autonomy from the start: complete autonomy isn't useful with no experience, so the reasonable target is enough built-in prior knowledge to be useful immediately, plus enough capacity to correct that prior against real percepts over time.

The clean mapping for LLM-agent design is the failure mode, not the fix: an agent following a rigid checklist that never re-checks its assumption against current observed state — a deploy script assuming a directory layout it never verifies — lacks autonomy in exactly the book's sense, failing the way the sphex wasp does, continuing to execute the plan as if a contradicting percept either wasn't received or wasn't looked at. Where the mapping stops being clean is the fix: the book's remedy is genuine learning, weights modified by experience across sessions. A single agent invocation has no equivalent — its weights don't update mid-task. The available analog at inference time isn't learning at all, it's *checking* — spending a tool call to verify a live assumption against current ground truth rather than trusting a prior belief from the system prompt or training data. That's a weaker guarantee, and it's worth being honest it's a different mechanism wearing the same name.

## Exploration falls out of the definition of rationality itself

The book separates this from "caution" as an extra virtue bolted on: "doing actions in order to modify future percepts — sometimes called information gathering — is an important part of rationality," falling directly out of maximizing expected performance under uncertainty rather than being an additional requirement layered on top. Looking before crossing isn't a safety add-on distinct from being rational — it *is* the rational action, because it improves the expected outcome of what follows, at low cost relative to what it protects against. A vacuum agent exploring geography it doesn't yet know, rather than restricting itself to squares already seen, is the same principle applied to an unknown environment in the strict PEAS sense: when an action's outcome is unknown, taking an action specifically to learn that outcome before committing to a costlier path is what expected-utility maximization requires, not a separate goal you remember to add.

For an LLM tool-calling agent this is close to a direct transfer: an agent that reads a file's current contents before editing it, checks test status before declaring a task done, or runs a status check before committing isn't doing "extra due diligence" layered on top of task completion — skipping a cheap, available check and acting on a stale or absent percept when a better one was one tool call away isn't efficient, it's irrational in the exact technical sense defined above. Cheap information-gathering calls — read-before-write, status-before-mutate, verify-before-commit — aren't friction to minimize for speed; they're how an agent under partial observability approaches the performance a fully observable agent gets for free.
