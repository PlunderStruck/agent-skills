# Legacy Code Change: An Operational Reference

Legacy code means code without tests — not old code, not ugly code; any code lacking a fast verification net counts. The goal is never "make it clean," it's "know immediately when I've broken something" — cleanliness becomes affordable only once that knowing exists. This reference corrects one failure mode: seeing untested, tangled code and reaching for a rewrite. A rewrite discards the one thing legacy code has going for it — it works, in ways nobody has fully enumerated. The alternative is smaller: find a seam, break one dependency at a time, pin current behavior down before touching it, and accept temporarily uglier code as the price of a verified one.

## 1. Core Concepts

**Edit and Pray vs. Cover and Modify.** Edit and Pray relies on understanding plus care: make the change, then poke around afterward hoping nothing broke. Cover and Modify wraps the target in tests first, so a fast run — not vigilance — reports what changed. System-level regression suites give this feedback too slowly and coarsely to localize which of several concurrent edits caused a failure; the target is narrow, unit-level feedback around the code being touched. Everything below exists to make Cover and Modify possible in code never built to allow it. The central bind: you often must edit code to get it under test, and editing untested code is exactly the risky move this discipline avoids — the way out is edits cheap and narrow enough that the risk of getting them wrong is smaller than the value of the seam they open.

**Seams and enabling points.** A seam is a place to substitute different behavior without editing the code at that place — this reframes the program as a set of exploitable substitution points running through otherwise-fixed text. A location only counts as a seam if more than one behavior could legally run there *and* something outside that line determines which one does — that second place is the seam's **enabling point**. A plain call, built and used within one scope with nothing able to swap the type, is not yet a seam; one has to be constructed, usually by relocating construction outward or making the target overridable.

Three types recur. **Object seams** exist wherever a call's target isn't fully pinned by the call's own text — the receiver arrived as a parameter, or the method is overridable — with the enabling point wherever the concrete instance gets chosen: a constructor argument, a factory, which subclass gets built. Default choice in any language with polymorphism or injection, since it's visible in source and needs no build cooperation. **Preprocessing seams** exist where a text-substitution stage runs before compilation (macros, conditional compilation, codegen); the enabling point is a build flag or alternate definitions file. Coarse, tied to languages with a literal preprocessing stage, reserved for otherwise-unreachable dependencies. **Link seams** exist where resolving a call happens later than compiling the caller — module resolution, dynamic or static linking; the enabling point is outside the source entirely, in a build script or search path. Effective against a dependency called from dozens of places, but invisible in a diff — keep the divergence conspicuous in the build setup. Prefer object seams by default; reach for the other two only when the obstruction is systemic.

**Sensing vs. separation.** Every testing obstacle reduces to one or both. *Separation*: the code can't run in a harness — construction drags in a network call, a database, or an object graph too large to build. *Sensing*: the code runs, but its effect can't be observed — swallowed by a collaborator (a display, a log) with no way to check it. Separation has many fixes, because there are many kinds of isolation obstacles — hence the catalogue below. Sensing has one recurring fix: a fake behind a seam — a stand-in collaborator satisfying the same narrow contract, recording what it was told instead of doing the real thing, so the test can assert against the recording (a mock additionally asserts internally rather than exposing state to inspect). A test built on a fake is still real — it won't catch a bug in the real collaborator, but proves this code produces the right calls with the right values.

**Characterization tests.** A characterization test records what code actually does right now, not what it's supposed to do — no notion of correctness, just a catch for future, undeliberate deviation. This is what makes it safe to touch code nobody understands: instead of reasoning toward the expected result, let the code compute it and pin that down as the new baseline.

## 2. The Change Procedure

**The five-step loop.** Every legacy change follows the same shape: (1) identify the change points — where the new behavior belongs; (2) find test points — where the effects can be observed; (3) break dependencies — get the change point, and enough around it, into a harness by exploiting a seam; (4) write characterization tests pinning current behavior before touching it; (5) make the change (TDD for genuinely new behavior) and refactor now that the area is covered. Treat this as a loop — tested regions accumulate as islands that grow together, so later changes nearby get cheaper. Step 3 is the uncomfortable one: an edit made before the safety net it's building exists, hence the stricter discipline below.

**Scoping what to test.** Don't test only the method being edited. Reason forward along the three channels an effect can travel: a return value read by a caller; a parameter object mutated and read later by whoever holds it; and shared or global state mutated and read elsewhere — the least visible, and likeliest to bite if not traced deliberately. Sketch it as a graph: a node for everything that could change, an arrow to everything it could affect downstream. Stop at a boundary the language genuinely enforces; where it's only assumed, keep tracing. When a change ripples across several classes, dependency-breaking each individually isn't mandatory — look for a pinch point, a method (or few) that all the scattered effects funnel through. Covering it buys temporary safety for the whole cluster; refactor underneath as long as those tests stay green, then replace them with narrower per-class tests as coverage grows.

**Writing a characterization test.** The procedure is mechanical, which is the point — it doesn't require understanding the code first. Exercise it in a harness. Write an assertion believed wrong, or none at all. Run it and let it fail. Read the actual value out of the failure output and paste it in as the expected result. Repeat for other inputs, especially boundary cases, and for each branch of a conditional separately rather than one test that only proves the common path ran. Where it's ambiguous whether a branch or an implicit conversion actually ran, add a throwaway instrumentation flag to confirm it, then discard it.

There's no fixed stopping point, since the input space is infinite. Stop in two passes: once genuine uncertainty about the behavior is resolved, then again after asking whether the current tests would catch a mistake at the specific change about to be made — if not, add more; if confidence still isn't reachable, shrink the change's scope instead of proceeding unprotected. If a bug turns up while characterizing: fix it outright if nothing depends on current behavior yet; if it's already in use, flag it and resolve the question before touching it — but still record what actually happens today as the test.

**Changing code safely before tests exist.** These edits happen without the net they're building, so they need a stricter discipline in its place: *single-goal edits* — do exactly one thing per edit, noting any second necessary change rather than interleaving changes that can't be mentally unwound independently; *preserve signatures* — when relocating code purely to open a seam, copy parameter lists and call sites exactly by cut-and-paste rather than retyping, saving real API cleanup for once the area is covered; *lean on the compiler* — deliberately break a declaration and let the resulting errors enumerate every call site that must change, rather than manually hunting (this proves structural consistency, not preserved behavior, and has blind spots); and *a second pair of eyes*, worth the cost here since this is the one category of edit with no automated net yet. Once characterization tests exist, this caution can relax.

**Matching obstacles to fixes.** Don't read the constructor looking for the problem — write a bare construction call with no assertions and let the compiler enumerate what's missing, then match the obstacle: an expensive constructor argument → extract a narrow interface and pass a fake; a dependency created directly inside the constructor → an overload accepting it as a parameter, original signature kept as a default-supplying wrapper; a dependency buried deep in construction → an overridable factory method (only where the language dispatches virtual calls during construction), or a post-construction swap otherwise; a pervasive singleton → a way to swap its backing instance for tests; a sealed library type → depend on the narrowest usable slice of its behavior. Once instantiable but one method still won't run: a private method is usually tested through its public caller, visibility loosened only as a last resort; a method with invisible effects gets peeled into named pieces separating computation from mutation, so unobservable pieces can be isolated and overridden; a method touching no instance state can be pulled into a static function; a long, tangled method belongs wholesale in its own small class (Break Out Method Object, below).

**Monster methods.** An oversized method resists testing as either bulleted (loosely related chunks with temp variables secretly threaded between them) or snarled (deep, hard-to-trace nesting). With a refactoring tool that guarantees behavior-preserving extraction, use it exclusively for the session — mixing in manual edits voids the guarantee. Without one: extract the smallest, most confidently nameable chunk first, preferring chunks with no values crossing the boundary since there's nothing to get wrong; for chunks that share state, add a throwaway sensing variable, write a quick test against it, extract, confirm, then delete the instrumentation. Keep new extractions on the current class even when they look like they belong elsewhere, and expect to redo early extractions once the emerging shape reveals a better cut.

**No structure.** Loss of structure is usually loss of shared understanding as much as tangled code — nobody holds the whole shape, so people patch wherever they last worked, compounding the drift. The fix isn't a rewrite or a single redesign; it's incremental, folded into ordinary work. Watch for a concept everyone names fluently in conversation but that has no corresponding code — a "policy" that's really just loose counters scattered across files — that's a missing class waiting to be extracted, one change at a time.

## 3. Technique Catalogue

Decision procedure before reaching into this catalogue: name the exact obstacle, never the general feeling that the code is bad. Ask, in order — (a) construction problem or invocation problem? (b) is the dependency touched from one call site or scattered across many — a single site takes a local fix, a dependency reached from dozens of places needs one shared seam introduced once, with the compiler used to find every remaining caller; (c) is this about testing existing behavior in place, or adding new behavior that shouldn't be entangled with untested code at all? For the third case, isolate the new logic behind the smallest possible seam instead of forcing the surrounding code under test first.

### Adding new behavior without testing the old code first

**Sprout Method** — *Use when* a change is a distinct, self-contained chunk of new logic expressible as one call from inside an existing untested method. *What you do*: write the call at its insertion point (commented out, to see it in context), pass whatever local state it needs as parameters, develop the new method test-first and fully decoupled from the surroundings, then enable the call; if the class can't be instantiated at all, make it a plain function instead. *Cost/risk*: the old method and class stay exactly as untested as before, and the wiring call site itself remains unverified.

**Sprout Class** — *Use when* Sprout Method isn't enough: the containing class's dependencies are too tangled to harness in reasonable time, or the new logic is a genuinely distinct responsibility. *What you do*: the same move, except the new code becomes a whole new class, constructed with only the state it needs, built and tested independently, then wired in through one call or construction site. *Cost/risk*: adds a class that can feel disconnected from the app's other concepts and may never fully reconcile into an obvious home — accepted because it's still safer than an invasive edit to unverifiable code.

**Wrap Method** — *Use when* new behavior must run strictly before or after an existing method's logic, without interleaving into it. *What you do*: either rename the old method and reintroduce its original name as a thin wrapper calling the new behavior plus the renamed original (transparent to callers), or leave the original alone and add a separately named method sequencing new-then-old for callers who opt in. *Cost/risk*: forces inventing a name for "the old code minus its old name," often mediocre until further extraction is safe.

**Wrap Class** — *Use when* behavior needs to wrap a method across many call sites, or just one or two, without adding to a class that shouldn't get any bigger. *What you do*: for many sites, build a class implementing the same interface as the original, holding a reference to it, defaulting to plain delegation and overriding only the operations needing new behavior — decorator-style, so wrappers compose; for one or two sites, a narrower one-off wrapper suffices. If the original has no interface yet, extract one first. *Cost/risk*: chains of wrappers get hard to trace; a one-off wrapper that keeps accreting responsibilities is really a future extraction being deferred.

### Breaking dependencies in existing code

**Extract Interface** — *Use when* a fake needs to stand in for a class dependency, and faking the concrete class directly isn't practical. *What you do*: declare a new, initially empty abstraction; make the real class satisfy it; change the reference at the point of use to the abstraction; then, driven only by what the compiler demands, add just the operations that call site uses, and write a fake behind it. *Cost/risk*: a new type that may map to no real domain concept at first; with non-virtual dispatch by default, moving a same-named method onto the abstraction can quietly change which implementation resolves elsewhere in a hierarchy.

**Parameterize Constructor / Parameterize Method** — *Use when* a constructor or method builds a collaborator internally, and that inline construction blocks substitution. *What you do*: add an overload accepting the collaborator as a parameter; keep the original signature as a thin wrapper supplying the real object by default. *Cost/risk*: widens the public surface with an extra overload and gives the rest of the codebase a new path to couple to the collaborator's concrete type — usually acceptable, which is why this is one of the most frequently reached-for techniques.

**Extract and Override Call** — *Use when* a single call inside a method — to a static, a global, or some other troublesome dependency — is the one thing blocking testing. *What you do*: wrap that call in a new same-signature method, replace the call site with a call to the wrapper, then override the wrapper in a test-only subclass. *Cost/risk*: cheap and safe, but doesn't scale past a handful of call sites for the same dependency — beyond that, centralize instead.

**Subclass and Override Method** — *Use when* one isolable piece of behavior — commonly object creation or a call into an unreachable dependency — blocks testing. *What you do*: find the smallest set of methods whose override would neutralize the problem, loosen their visibility and make them overridable, then subclass for tests and override just those. *Cost/risk*: the foundational move underneath most of the others, so use restraint — widening visibility on intentionally private methods is a real cost, and over-aggressive overriding means the test no longer exercises the class's actual behavior.

**Introduce Instance Delegator** — *Use when* the blocking dependency is a static or utility call with no object to substitute. *What you do*: add an instance method that forwards to the existing static call, then migrate call sites to go through an instance instead. *Cost/risk*: leaves an interim, odd mix of statics and thin pass-through methods until every caller migrates, and creates a second problem — how each site now obtains that instance.

**Break Out Method Object** — *Use when* a method is long and entangled with instance state, and its class is too costly to instantiate for a test. *What you do*: create a class whose constructor takes a reference to the original object plus the method's original parameters as fields; move the body verbatim into a "run"-style method; expose whatever original-class members it still touches; delegate the original method to an instance of the new class. *Cost/risk*: loosens encapsulation on the source class and produces an odd interim shape, accepted because former locals become fields that can now be sensed freely.

**Expose Static Method** — *Use when* a method uses no instance state, but its class is very hard to instantiate. *What you do*: extract the method's body into a public static or free function, and let the original delegate to it. *Cost/risk*: makes something conceptually tied to an instance callable from anywhere; if the logic doesn't truly belong on this class, exposing it can entrench it there.

**Adapt Parameter** — *Use when* a parameter's type is wide, external, or unmodifiable and not narrowable with Extract Interface directly. *What you do*: define a small abstraction expressing only the subset of behavior actually needed, write a production adapter wrapping the real parameter, write a fake behind the same abstraction, and change the method to accept it. *Cost/risk*: the one technique here that doesn't preserve the original signature, so every caller must change; if the narrowed abstraction doesn't faithfully mirror the original's semantics, this can introduce a real behavioral bug, not just a testing convenience.

**Encapsulate Global References** — *Use when* logic depends on several scattered globals or free functions, and no single call-site fix covers all the uses. *What you do*: identify globals used together conceptually, create a class to own them under their original names to minimize churn, let the compiler point out every now-broken reference, and redirect each through the new owning object; once centralized, apply a substitution technique to swap in a fake under test. *Cost/risk*: deliberately ugly at first — a single global object standing in for several globals isn't a design improvement by itself, only a staging point.

**Pull Up Feature / Push Down Dependency** — *Use when* a class mixes a few methods needing tests with an unrelated, heavy dependency — a database call, a hardware handle. *What you do*: split the class along that line — move the testable methods up into a new abstract superclass and test through a lightweight subclass, or push the dependency-laden members down into a subclass and test the freed base directly. *Cost/risk*: splits one class across two types purely for testability, which can read as arbitrary if the halves aren't conceptually related — interim, pending a proper composition-based cleanup.

**Extract and Override Factory Method** — *Use when* a constructor buries creation of a dependency to replace, in a language where a constructor's virtual calls dispatch to subclass overrides. *What you do*: move the creation into an overridable factory method and override it in a test subclass. *Cost/risk*: doesn't work where base construction can't reach derived overrides yet (notably C++) — there, defer creation behind a lazily-initializing getter and override that, or, if the dependency is also used elsewhere in the constructor, add a distinctly named method that swaps the field after construction, called only from test setup; that variant weakens the invariant that a dependency is fixed for the object's lifetime.

Across the catalogue, the trade is the same: accept a small, named, temporary ugliness — an extra overload, a wrapper class, a loosened access modifier — for a seam that makes surrounding behavior verifiable. Each technique is the cheapest move that removes one specific, named obstacle, setting up a cleaner refactor later, once tests exist to protect it.
