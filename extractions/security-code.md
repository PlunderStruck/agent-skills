# Code-Level Security: Vulnerability Classes and Concrete Fixes

Scope note: this covers coding-time mistakes — the exact shape of vulnerable code, why the mechanism fails, the correct fix, and how to check for it. It does not cover system design, threat modeling, or organizational controls.

## 1. Injection (SQL, OS Command, LDAP)

**Trigger.** SQL: building a query by concatenating or interpolating user input into a string before execution — `"SELECT * FROM users WHERE name = '" + name + "'"`. OS command: passing a string built from user input to a shell-invoking API — `os.system("convert " + filename)`, `subprocess.call(cmd, shell=True)`, `Runtime.exec("cmd /c " + input)`. LDAP: building a search filter or DN by concatenation — `"(&(uid=" + user + ")(objectClass=person))"`.

**Why it fails.** In all three cases the interpreter (SQL parser, shell, LDAP filter parser) cannot distinguish "code" from "data" once they're merged into one string — special characters in the input (`'`, `;`, `|`, `&`, `*`, `)`, backticks) are re-interpreted as syntax. For SQL this rewrites the query logic; for shells it chains additional commands or, even when metacharacters are blocked, injects extra *arguments* into the intended command (argument injection); for LDAP it restructures filter logic (e.g., `*` or `)(uid=*` to broaden a match).

**The fix.** Parameterization, not escaping. Use `PreparedStatement`/parameterized query APIs (`?` or named placeholders bound via `setString()`, `bindParam()`, ORM `setParameter()`) so the query structure is compiled before data arrives — the database never re-parses the value as SQL. Escaping is explicitly the weaker, fallback option: escape rules are database- and encoding-specific and are routinely bypassed by encoding tricks; treat it as a last resort, not a peer alternative. Table/column names and sort direction cannot be parameterized (binds only cover values) — resolve those through a hardcoded switch/allowlist mapping user input to a known-safe identifier, never by appending the raw value. For commands, avoid the shell entirely: call APIs that take an argument array and execute directly (`subprocess.run([...], shell=False)`, `ProcessBuilder("cmd","arg1","arg2")`), since each array element is passed as one atomic argument, not reparsed for shell syntax. If a shell is unavoidable, use `escapeshellarg()`-style quoting *and* a strict allowlist of both the executable and argument format (e.g. `^[a-z0-9]{3,10}$`). For LDAP, use a parameterized filter API where the library escapes bound values per RFC 4515/2253, or explicit encoder functions (`encodeForLDAP`, `encodeForDN`) — never hand-rolled character stripping. Everywhere: run the DB/LDAP account with least privilege (no DBA rights, scoped views/OUs) so a missed case has bounded blast radius.

**How to verify.** Grep for string concatenation or f-strings feeding into `execute`/`query`/`system`/`exec`/`ctx.search` calls; grep for `shell=True`, `Runtime.exec("... +`, `os.system(`. Confirm every stored procedure avoids dynamic SQL (`sp_executesql`, `EXEC(@sql)`) built from parameters. Functional test: submit `' or '1'='1`, `; rm -rf /tmp/x;`, and `*)(uid=*` as values and confirm they're treated as inert data, not reinterpreted syntax.

## 2. Cross-Site Scripting and DOM-Based XSS

**Trigger.** Reflected/stored XSS: untrusted data written into an HTML response without encoding matched to its output context — `<div>` + userInput + `</div>`, or into an attribute, inline `<script>`, inline CSS, or a URL. DOM XSS: untrusted data (from `location.hash`, `document.referrer`, `postMessage`, or any client-side input) flowing into a dangerous DOM sink: `innerHTML`, `outerHTML`, `document.write()`, `eval()`, `setTimeout(stringArg)`, `element.setAttribute("onclick", ...)`, React's `dangerouslySetInnerHTML`, Vue's `v-html`, Angular's `[innerHTML]` after `bypassSecurityTrustHtml`.

**Why it fails.** The browser parses HTML, JavaScript, CSS, and URLs with different grammars. An encoding scheme correct for one context is often a no-op or actively wrong in another: HTML-entity-encoding data placed inside a `<script>` block does not stop execution, because the browser doesn't HTML-decode script bodies the same way — the payload can still close the intended string and inject a new statement. Encoding is therefore not one operation but a family of operations, and picking the wrong one silently leaves the hole open. Certain contexts are unsafe *at any encoding level* — directly inside `<script>` or `<style>` tags, inside an HTML comment, as a tag/attribute name, inside an event-handler attribute, or inside CSS `url()` — because the value can break out of "data" regardless of escaping.

**The fix.** Match the encoder to the sink: HTML entity encoding for element content (`&`,`<`,`>`,`"`,`'`), HTML attribute encoding (`&#xHH;`) for attribute values, JavaScript Unicode encoding (`\uXXXX`) only for data placed inside a quoted JS string literal, CSS hex encoding for a CSS property value, and URL percent-encoding for a query parameter — applied in that order when contexts stack (e.g. URL-encode, then attribute-encode a `href`). Prefer safe sinks over encoding entirely: `textContent` instead of `innerHTML`, `setAttribute()` with a hardcoded attribute name, `createElement()`/`createTextNode()` DOM construction. If raw HTML from a user must render, run it through an allowlist HTML sanitizer (DOMPurify) at the point of insertion — not upstream, and not once at request-intake, since neither knows the final render context. Framework auto-escaping (React JSX, Vue `{{ }}`, Angular interpolation) is the default-safe path; the moment code reaches for an escape hatch (`dangerouslySetInnerHTML`, `v-html`, `bypassSecurityTrustHtml`, `unsafeHTML`), that boundary is manual again and needs the same scrutiny as raw string concatenation.

**How to verify.** Grep for `innerHTML`, `outerHTML`, `document.write`, `eval(`, `dangerouslySetInnerHTML`, `v-html`, `bypassSecurityTrust`. For every hit, trace the source: is it a literal, or does it reach a user-controlled value (URL, form field, API response, `postMessage`)? Test with payloads specific to context: `<img src=x onerror=alert(1)>` in body context, `" onmouseover="alert(1)` in attribute context, `');alert(1);//` in script context.

## 3. Insecure Deserialization

**Trigger.** Feeding untrusted bytes into a language's native object deserializer: Java `ObjectInputStream.readObject()`, `XMLDecoder`, `XStream.fromXML()`; Python `pickle.loads()`; PHP `unserialize()`; Ruby `Marshal.load`; .NET `BinaryFormatter`, or `JSON.Net` with `TypeNameHandling` set to anything but `None`.

**Why it fails.** Native deserialization reconstructs objects by invoking constructors and "magic methods" (`__wakeup`, `__destruct`, `__reduce__`) as part of rebuilding the object graph. Attackers don't need a bug in your code — they chain together classes already present on the classpath/environment ("gadget chains") whose side effects, when triggered in sequence during deserialization, execute arbitrary code. The vulnerability is structural to the format, not a missing check.

**The fix.** Don't deserialize untrusted data with the native/binary mechanism at all — use a data-only format (JSON/XML) validated against a strict schema, which has no code-execution hooks. If a native format is unavoidable (legacy interop), enforce class allowlisting before reconstruction (override `resolveClass()` in Java to reject anything outside an expected type set) and only deserialize data that carries a cryptographic signature verified *before* deserialization begins — never sign-then-trust-then-deserialize-then-check.

**How to verify.** Grep for `readObject(`, `pickle.load`, `unserialize(`, `Marshal.load`, `BinaryFormatter`, `TypeNameHandling` set to non-`None`, `yaml.load` (vs. `safe_load`). Watch for these landing on any value that originated from a request body, cookie, or file upload.

## 4. Server-Side Request Forgery (SSRF)

**Trigger.** The server fetches a URL that is user-supplied or user-influenced: webhook registration, "fetch image from URL," PDF/screenshot generators, link-preview features.

**Why it fails.** The server has network reach the outside attacker doesn't — internal services, admin panels, localhost ports, and cloud metadata endpoints (`169.254.169.254`), which often hand out credentials with no additional auth. The application becomes an unwitting proxy into its own private network.

**The fix.** Default to an allowlist of permitted destinations (specific hosts/IPs), not a denylist of "known-bad" ranges — denylists are bypassed by alternate IP encodings, DNS rebinding, and redirects, and internal ranges keep expanding. Disable automatic redirect-following in the HTTP client, or re-validate the destination after every redirect hop. Resolve the hostname and check the *resolved* IP is not private/loopback/link-local before connecting, not just the string the user typed. Validate the response (content-type, size) as well as the request. Pair this with network-layer egress restrictions from the app tier as defense-in-depth — but don't treat the firewall as the only control.

**How to verify.** Grep for HTTP client calls whose URL argument traces to request input. Test with `http://169.254.169.254/`, `http://localhost:PORT/`, decimal/octal IP encodings, and a redirect chain ending at an internal address.

## 5. Authentication, Session Management, and Password Storage

**Trigger.** Login/reset endpoints that return different messages or timings for "user doesn't exist" vs. "wrong password"; password comparison via plain `==`/`.equals()`; no attempt-rate limiting; sensitive actions (email/password change) performed without re-entering credentials; session IDs generated from a non-cryptographic RNG or from timestamps; session cookies missing `Secure`/`HttpOnly`/`SameSite`; session ID not regenerated after login.

**Why it fails.** Differing responses or response times leak whether a username is valid (enumeration), letting an attacker narrow a credential-stuffing target list. Non-constant-time comparison leaks the correct value byte-by-byte via timing. Predictable or low-entropy session IDs can be brute-forced or guessed outright. A session ID accepted from the client without regeneration at login enables session fixation: an attacker plants a known ID, waits for the victim to authenticate under it, and the attacker's copy is now privileged. A missing `HttpOnly` flag lets any XSS bug exfiltrate the session cookie via `document.cookie`.

**The fix.** Return one identical message and response-time profile ("if that account exists, we've sent an email") for every failure case in login and reset flows. Use library-provided constant-time comparison for anything security-sensitive (or better, avoid manual comparison by hashing correctly, see below). Generate session identifiers with a CSPRNG carrying at least 64 bits of entropy. Regenerate the session ID on every authentication and privilege-level change (`session_regenerate_id(true)`, `HttpSession.invalidate()` + new session). Set cookies with `Secure`, `HttpOnly`, and `SameSite=Strict` or `Lax`; never put session identifiers or PII in the cookie value itself, only an opaque reference. Enforce both an idle timeout and an absolute timeout server-side. On logout, invalidate the session server-side (not merely clearing the client cookie) and send `Clear-Site-Data`. Require re-entry of current credentials (or MFA) before changing password, email, or payment details.

**Password storage — current guidance.** Never store passwords in plaintext or reversible encryption, and never rely on a general-purpose fast hash (MD5/SHA-1/SHA-256) alone — those are engineered to be fast, which is precisely the wrong property for password verification, since it lets an attacker with a stolen hash database try billions of guesses per second on commodity or GPU hardware. Use a dedicated, deliberately slow and memory-hard password hash. Current preference order and minimum parameters: **Argon2id** with memory ≥ 19 MiB, iterations = 2, parallelism = 1 (heavier profiles such as 46 MiB/1 iteration are also acceptable trade-offs); **scrypt** with N=2^17 (128 MiB), r=8, p=1 as a fallback; **bcrypt** with cost factor ≥ 10 only for legacy stacks that can't add Argon2id; **PBKDF2-HMAC-SHA256** at 600,000 iterations (or PBKDF2-HMAC-SHA512 at 220,000) only where FIPS-140 compliance forces it — it's the weakest of the four against GPU attacks because it isn't memory-hard. Salting must be unique per user and is handled automatically by all of the above libraries — don't hand-roll it. A shared application-wide "pepper" is optional defense-in-depth; if used, store it outside the database (secrets manager/HSM), never alongside the hash. Rehash-on-login when parameters are strengthened: keep the old verifier working, and replace it with a hash under the new parameters the next time that user authenticates successfully.

**How to verify.** Grep for `MD5(`, `SHA1(`, `SHA256(` applied to a password field, and for `==`/`.equals(` comparing anything called `password` or `token`. Confirm the hashing call names Argon2id/bcrypt/scrypt/PBKDF2 with parameters at or above the minimums above. Test that login/reset error text and latency are indistinguishable for valid vs. invalid usernames. Confirm session ID changes across the login boundary via cookie inspection.

## 6. Authorization, Access Control, and Insecure Direct Object Reference

**Trigger.** An endpoint checks that the caller is *authenticated* but not that the caller is *permitted* to act on the specific object requested — `Project.find(params[:id])` instead of `current_user.projects.find(params[:id])`. Or authorization logic exists only in the UI (hidden button) rather than being re-checked server-side. IDOR specifically: a client-supplied ID (`GET /accountTransactions?acct_id=901`) is used to fetch a record with no ownership check, so changing the ID to `523` returns someone else's data.

**Why it fails.** Authentication proves *who* the caller is; it says nothing about *what* they may touch. Without a per-object check on every request, any authenticated user can reach any object simply by changing an identifier, because nothing in the request path validates the relationship between caller and object. Obscuring IDs (making them random) reduces guessability but is not a substitute for the check — it's still bypassable by anyone who legitimately obtained one ID (their own) and tries another.

**The fix.** Default-deny: every route decides explicitly to permit or reject, rather than falling through to allowed. Enforce the check server-side, at the point of data access (repository/query layer), not only in routing middleware — middleware answers "can this role hit this route," not "does this user own this row." Scope every fetch to the authenticated user's own records at the query level (`WHERE user_id = current_user_id()`), so a wrong ID returns "not found" rather than someone else's data. Apply the same discipline to both horizontal (peer user's data) and vertical (elevated role's functionality) escalation paths — a role check on the route and an ownership check on the row are two different, both-required controls.

**How to verify.** For every state-mutating or data-returning endpoint, write a test as a second, lower-privileged/different user attempting to read or modify the first user's object by ID; expect a rejection, not data. Grep for query methods (`.find(`, `.findById(`) not scoped by a current-user/tenant filter.

## 7. Cryptographic Storage, Key Management, and Secrets Management

**Trigger.** Custom/homemade encryption algorithms; ECB mode; DES/RC4; a hardcoded key or IV baked into source; an IV/nonce reused across encryptions with the same key; an encryption key stored in the same table/file as the ciphertext it protects; API keys, DB passwords, or private keys committed to source control or left in a Dockerfile `ENV`.

**Why it fails.** ECB leaks structural patterns in the plaintext because identical blocks encrypt identically. IV reuse under most stream/CTR-style modes lets an attacker XOR two ciphertexts to recover plaintext relationships. A key stored beside its ciphertext means anyone who reads the data store gets both halves — the encryption adds no real barrier. A secret in git history persists even after the offending commit is reverted or a later commit deletes the line — the blob is still retrievable from history by anyone with clone access, indefinitely.

**The fix.** Use AES with authenticated encryption (AES-GCM, or ChaCha20-Poly1305) rather than plain CBC — AEAD gives you confidentiality and tamper-detection (integrity/authenticity) in one primitive, so a modified ciphertext fails to decrypt instead of silently decrypting to garbage or attacker-controlled bytes. Minimum key size 128 bits, 256 preferred; for asymmetric, RSA ≥ 2048 bits or modern curves. Let the crypto library generate IVs/nonces via its CSPRNG — don't construct them manually, and never reuse one with the same key. Keep the distinction sharp: encrypt data you need to *read back* (must be reversible); hash data you only need to *verify* (passwords — irreversible by design, see §5). Never "encrypt" a password as a substitute for hashing it — that's reversible by definition and defeats the point. Store keys in a dedicated KMS/HSM or secrets manager, separate from the data they protect, with rotation and access auditing; wrap exported keys with a key-encryption-key. For application secrets generally, inject at runtime (vault, environment injected by the orchestrator, not baked into the image) rather than embedding in source or build artifacts, and use short-lived, dynamically issued credentials where the backing service supports it. If a secret does land in git history: rotating the credential is mandatory — deleting the line or even rewriting history doesn't retroactively un-expose a secret that may already be cached, forked, or scraped.

**How to verify.** Grep for `DES`, `RC4`, `ECB`, `new IvParameterSpec(` with a literal byte array, and any `String KEY =`/`API_KEY = "` literal. Run a secrets scanner (detect-secrets, truffleHog, git-secrets) as a pre-commit hook and against full history. Confirm the cipher mode named in code is GCM/CCM/Poly1305, not CBC/ECB without a separate MAC.

## 8. Transport Layer Security

**Trigger.** TLS 1.0/1.1 (or SSLv2/v3) still enabled; certificate validation disabled for convenience and left that way — `verify=False` in `requests`, `NODE_TLS_REJECT_UNAUTHORIZED=0`, a custom trust manager that accepts anything.

**Why it fails.** TLS 1.0/1.1 are formally deprecated (RFC 8996) and carry known weaknesses; leaving them enabled means a downgrade attack can force the connection to the weaker protocol. Disabling certificate validation removes the entire guarantee that you're talking to the server you think you are — it converts TLS into unauthenticated encryption, trivially defeated by a machine-in-the-middle.

**The fix.** Require TLS 1.2 minimum, prefer 1.3; disable everything older explicitly rather than relying on defaults. Use AEAD cipher suites (AES-GCM, ChaCha20-Poly1305); disable null, anonymous, export-grade, and non-forward-secret suites. Never ship a "skip verification" flag that was added for local testing — gate it behind an environment check that cannot reach production, or better, remove it and use a real (even self-signed-but-pinned) cert locally. Add HSTS so browsers refuse to downgrade even if a link is HTTP.

**How to verify.** Grep for `verify=False`, `rejectUnauthorized: false`, `NODE_TLS_REJECT_UNAUTHORIZED`, `InsecureSkipVerify`, or custom `TrustManager`/`HostnameVerifier` implementations that return true unconditionally. Run testssl.sh or SSL Labs against the deployed endpoint.

## 9. Input Validation

**Trigger.** Validating input by checking it *doesn't* contain a list of known-bad substrings or patterns (denylist), rather than checking it matches a known-good shape.

**Why it fails.** A denylist enumerates attacks you've already thought of; encoding variants, alternate syntaxes, or simply attacks not yet imagined sail through untouched, while the same filter frequently rejects legitimate input it wasn't designed to anticipate (an apostrophe in `O'Brian`).

**The fix.** Validate positively: define exactly what's acceptable — type, length/range, and either a strict character-class regex anchored at both ends (`^[A-Za-z0-9_-]{1,32}$`, never an unanchored or wildcard-heavy pattern) or membership in a fixed enumeration for closed value sets. Layer syntactic validation (is it shaped like a date/SSN/email) with semantic validation (is the date in a sane range, does start precede end). For genuinely free-form text, normalize to a canonical Unicode form and allowlist character *categories* (letters, digits, common punctuation) rather than trying to enumerate every valid character. Always enforce this server-side — client-side validation is a UX convenience, trivially bypassed by disabling JS or replaying the request directly.

**How to verify.** Grep for `if.*contains.*blacklist` style filters or regexes with `.` / `\S` wildcards standing in for a proper character class. Confirm every server-side entry point re-validates, even when a client-side check exists.

## 10. File Upload and Path Traversal

**Trigger.** Trusting the client-supplied filename, extension, or `Content-Type` for an upload; storing the file under the user-supplied name inside the webroot; building a file-system path by concatenating a user-supplied filename or path segment onto a base directory — `open(base_dir + "/" + user_filename)` — without checking for `../`.

**Why it fails.** `Content-Type` and filename are attacker-controlled strings, not facts; an uploaded `.php`/`.jsp` file stored under its original name inside a served directory can be requested and executed by the attacker directly. A path built by naive concatenation lets `../../etc/passwd` or an absolute path walk outside the intended directory, because string concatenation doesn't understand filesystem semantics — only path resolution does.

**The fix.** Validate the extension against an allowlist of business-required types, then independently verify the *actual* file content via magic-byte/signature checking — extension and declared MIME type are claims, not proof. Generate the stored filename yourself (UUID), discarding the client's name entirely, and store outside the webroot (or in a location with execution disabled and least-privilege permissions); enforce a size limit; scan with antivirus before making the file servable. For paths: resolve the final path (`realpath`/canonicalize) and explicitly assert it is still a descendant of the intended base directory before touching it, or use a library "safe join" helper that refuses to leave the base — never trust a substring check for `..` alone, since encoding and symlink tricks can slip past naive filters.

**How to verify.** Grep for file APIs (`open(`, `File(`, `fs.readFile(`) whose path argument concatenates a request parameter. Test uploads with double extensions (`shell.php.jpg`), null-byte-suffixed names, and path payloads (`../../../etc/passwd`, absolute paths, URL-encoded traversal) and confirm rejection or containment.

## 11. Cross-Site Request Forgery

**Trigger.** A state-changing action reachable via a plain `GET`, or a `POST`/`PUT`/`DELETE` handler that performs the action based solely on a valid session cookie, with no additional per-request proof that the request originated from the application's own page.

**Why it fails.** Browsers attach cookies automatically to any request to a site, including ones triggered by a third-party page the victim happens to have open — the server can't tell "the user clicked a button on our site" from "a hostile page's auto-submitting form fired a request that happened to carry the user's cookies," because the cookie alone doesn't prove intent.

**The fix.** Synchronizer token pattern: issue a unique, unpredictable, per-session token, embed it in forms/AJAX calls, and reject any state-changing request where the submitted token doesn't match the session's token server-side — validated on *every* such request, not a sample. `SameSite=Lax`/`Strict` on the session cookie is valuable defense-in-depth but not sufficient alone: `Lax` still allows the cookie on top-level GET navigations, so any state change reachable by GET bypasses it entirely, and it only constrains cross-*site* requests, not same-site subdomain abuse or client-side (DOM-driven) CSRF. For stateless/API clients, a signed double-submit cookie (HMAC-bound to session data, not a naive raw match) or a custom header requirement (`X-CSRF-Token`) works, because simple cross-site form submissions cannot set custom headers — only same-origin script can, and that triggers a CORS preflight the server can gate on.

**How to verify.** Grep for `@GetMapping`/route handlers performing writes. Confirm token validation exists on every POST/PUT/DELETE/PATCH handler, not just a subset. Test that a request missing or replaying a stale token is rejected, and that GET never mutates state.

## 12. Mass Assignment

**Trigger.** Binding an entire request body directly onto a model/entity without restricting which fields are settable — `User.update(req.body)`, `User.create({...req.body})`, or a Spring MVC handler taking a full domain object as its parameter with no field allowlist.

**Why it fails.** Framework auto-binding convenience maps every JSON key to a matching object property by name. If the domain object has an `isAdmin` or `role` field for internal use, an attacker only needs to add `"isAdmin": true` to the request body — the binder does the rest, with no code anywhere having asked for that field to be settable by a client.

**The fix.** Never bind directly onto a persistence entity from external input. Bind onto a purpose-built DTO/request object that only contains the fields the endpoint intends to accept, or use framework-level allowlisting (Rails `strong_parameters`/`fillable`, Spring `@InitBinder` + `setAllowedFields`) to explicitly name what's bindable.

**How to verify.** Grep for `req.body` (or equivalent) spread directly into a `create`/`update`/`save` call, and for domain-object parameters on write endpoints with no accompanying allowlist annotation.

## 13. XML External Entity (XXE)

**Trigger.** Parsing attacker-supplied XML with a parser left at default settings, which typically resolve `DOCTYPE`/`ENTITY` declarations — `<!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd">]><foo>&xxe;</foo>`.

**Why it fails.** Most XML parser defaults predate today's threat model and will fetch whatever a `SYSTEM` entity points to — a local file, or an internal/external URL (turning XXE into SSRF), or a recursively-expanding entity that exhausts memory (billion-laughs).

**The fix.** Disable DTD processing and external entity resolution outright, per parser: Java `DocumentBuilderFactory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)` plus disabling general/parameter external entities; Python's `defusedxml` instead of the stdlib parser; .NET `XmlReaderSettings.DtdProcessing = DtdProcessing.Prohibit` with `XmlResolver = null`; PHP `libxml_set_external_entity_loader(null)` (default-safe from PHP 8.0). Disabling DTDs entirely is the recommended default even when entities aren't a business requirement.

**How to verify.** Grep for `DocumentBuilderFactory`/`SAXParserFactory`/`XMLReader` construction without the disable-DTD feature call, and for any XML parse call reachable from request input.

## 14. REST and GraphQL API Security

**Trigger.** REST: no HTTP-method allowlist (unexpected verbs silently accepted), no request size/rate limiting, `Content-Type` copied from the request `Accept` header, JSON responses returning full internal objects. GraphQL: unbounded query nesting/depth, batched queries requesting large ID ranges in one call, introspection left enabled in production, authorization checked only at the top-level query, not per resolver/field.

**Why it fails.** Both patterns share a root cause: the API trusts the shape and cost of a client-composed request. An unbounded GraphQL query can force the server to resolve an attacker-chosen number of nested objects in one round trip — no single "endpoint" was ever explicitly exposed, but the schema graph makes an unbounded fan-out query graph reachable. A field-only authorization check at the top of a resolver tree misses nested objects reached through relationships, e.g. reading another user's private data via a nested `author` field on a post the caller does own.

**The fix.** REST: allowlist accepted methods and reject the rest with `405`; enforce request size and rate limits per authenticated identity, returning `413`/`429`; validate `Content-Type` against an allowlist rather than echoing `Accept`; use `403` (not `404`) for authorization failures so behavior doesn't leak resource existence, and never surface stack traces in the body. GraphQL: enforce a maximum query depth and a cost/complexity budget before execution (`graphql-depth-limit`, cost-analysis instrumentation), apply a server-side timeout, disable introspection and any GraphiQL UI in production, and re-run the object-level authorization check inside every resolver that returns a distinct object — not just at the query root.

**How to verify.** Send disallowed HTTP verbs and confirm `405`; send an oversized payload and confirm `413`. For GraphQL, submit a deeply nested or high-`first:` query and confirm it's rejected or times out; confirm `__schema` introspection queries fail in production; test resolver-level authorization by requesting a nested relation belonging to another tenant/user.

## 15. Logging, Error Handling, and Supply Chain

**Trigger.** Logging: writing passwords, session tokens, API keys, full auth headers, or payment data to logs; writing raw user input into a log line without stripping newlines, letting the input inject forged log entries. Error handling: returning a raw stack trace, SQL error text, or framework/version banner directly in an HTTP error response. Supply chain: adding dependencies without pinning versions, never scanning for known-vulnerable packages, no lockfile.

**Why it fails.** Logs are frequently shipped to less-trusted systems (aggregators, tickets, support screenshots) than the app itself, so secrets logged there leak through a wider surface than the original bug. Unsanitized input containing `\r\n` lets an attacker forge fake log lines that look like legitimate entries, undermining audit trails. A stack trace or DB error tells an attacker your framework, version, and sometimes your schema — reconnaissance you handed over for free. Unpinned/unscanned dependencies mean a known CVE in a transitive package ships silently, and there's no lockfile to reproduce or roll back a bad update.

**The fix.** Maintain an explicit list of fields that must never be logged (credentials, tokens, keys, card/PII data) and redact/hash them before the log call; strip or encode CR/LF and delimiter characters from any user-controlled value before it enters a log line, or use structured (JSON) logging where fields can't bleed into each other. Do log security-relevant events themselves — auth successes/failures, authorization failures, input-validation failures — since that's the audit trail you actually want. Centralize exception handling so every unhandled error returns one generic message to the caller (`"An error occurred, please retry"`) while the full exception, with context, goes only to server-side logs. For dependencies: use lockfiles for reproducible installs, run an SCA scanner (`npm audit`, OWASP Dependency-Check, Trivy, Snyk) in CI, enable automated update tooling (Dependabot/Renovate) so patches land quickly, verify package integrity via checksums/signatures where the ecosystem supports it, and generate an SBOM for anything shipped externally.

**How to verify.** Grep logs/log-call sites for `password=`, `token=`, `api[_-]?key`, `Authorization:` — should return nothing live. Grep error handlers for direct exception serialization into an HTTP response (`e.printStackTrace()` to the client, `res.send(err.stack)`). Run the ecosystem's audit command and confirm CI fails the build on high/critical findings; confirm a lockfile is committed and enforced (`npm ci`, not `npm install`, in CI).
