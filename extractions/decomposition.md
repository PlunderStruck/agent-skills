# Decomposition: When to Split, When Not To

Operational rules extracted from *Thinking Forth*, restated without Forth's stack/word mechanics. Each rule: the situation that triggers it, the concrete cost of getting it wrong, the move to make, and the question to ask afterward.

## 1. Understand the problem before you touch the boundary

**Rule: a boundary needs a reason — reuse or independent change.** Trigger: you're about to split code into pieces. What goes wrong: if you split along any other axis — most commonly "this runs before that" — the seams look organized on a diagram but don't correspond to anything real. A later change ripples across every piece because none of them actually owns the thing that changed. What to do: for each candidate boundary, name the specific thing that would make it earn its keep — a second caller that would reuse it, or a requirement likely to change independently of its neighbors. If you can't name one, it isn't a boundary yet. How to check: don't just inspect the split — subject it to one plausible future requirement change on paper and see whether the change stays inside one piece or forces edits across several. A decomposition that only looks clean has not been tested.

**Rule: fix interfaces and error-handling policy before decomposing anything else.** Trigger: you're about to divide a system into components while the shape of "what happens when something goes wrong" is still open. What goes wrong: error handling isn't a local decision — whether failures are surfaced, swallowed, retried, or halted changes the shape of nearly every unit's signature. Deciding it after the pieces exist means reworking all of them. What to do: settle inputs, outputs, and failure behavior for the system's outer boundary first, even while the internal design stays loose. How to check: can you describe what happens on bad input without opening any particular module's implementation?

**Rule: don't decompose a mess — simplify it first.** Trigger: a requirement arrives as a tangle of interacting conditions (rate tables, mode matrices, nested exceptions). What goes wrong: decomposing the tangle as given just distributes the tangle across more places. What to do: separate the independent dimensions buried in the requirement, check each dimension's cases are actually exhaustive and mutually exclusive, and look specifically for a dimension that's really a parameter to one calculation rather than a grid of special cases. How to check: you haven't finished understanding the problem until you can restate it more simply than however it was handed to you. If you can't compress it, you're not ready to split it.

## 2. Choosing the boundary

**Rule: group by what changes together, not by what happens in sequence.** This is the single most concrete lesson in the source material. A text editor built as "edit stage → refresh-display stage" looks clean: each pipeline stage is its own box, refresh is decoupled from any specific edit. But when the requirement changed from whole-screen refresh to incremental refresh, the refresh logic had to know exactly which edit happened — and the pipeline boundary, which had deliberately hidden that information, had to be torn open and re-scattered into every edit operation. A rival design that instead grouped "mutate the data" and "update what it affects" inside each edit operation absorbed the same change as one added line per operation. Trigger: a system suggests an obvious temporal shape (input → process → output, or step 1 → step 2 → step 3). What goes wrong: sequence-shaped boundaries survive review but not requirements changes, because the axis they're organized around (order) usually isn't the axis that changes. What to do: ask what data or behavior would have to move together if a specific detail changed, and draw the line around that, not around execution order. How to check: same as above — try a real change and see what it touches.

**Rule: data read or written by two or more components needs an owner.** Trigger: two pieces share a structure — a buffer, a shared record — and each currently pokes it directly. What goes wrong: both sides quietly develop their own understanding of what the structure means; a change to one side's assumptions breaks the other with no compiler or reviewer able to see why. What to do: give the shared structure, plus the operations that manipulate it, a home of its own that both sides call into. Express what crosses that boundary in terms meaningful to the problem (degrees, not raw sensor counts) so a different implementation on either side wouldn't force the other to change.

**Rule: not everything read across a boundary is legitimate shared state.** A margin-width value, set by a formatting module and read by an output module, looks like ordinary shared interface data — until the formatting module is free to change it between the read and the moment the output module still needs it, silently corrupting output that was already "done." Trigger: a value is genuinely private, freely-mutable state of one module, but a second module reaches in and reads it anyway. What to do: ask whether the producer can legitimately change the value while the consumer's result is still in flight. If yes, it isn't a stable interface value — freeze a snapshot for the consumer instead of handing over a live variable.

**Rule: a good name doesn't prove the boundary is sound — check the protocol too.** An allocator with cleanly named `allocate` and `mark` operations still leaked its internal direction-of-growth decision, because every one of twenty call sites was implicitly required to call `allocate` before `mark`. When allocation direction reversed, all twenty sites needed editing anyway. Trigger: you've named the pieces and assume the decision behind them is hidden. How to check: could the internal decision flip with zero change to the *order* callers must invoke things in? If not, the abstraction leaks through its calling convention, not just its name.

## 3. Signals a chunk is secretly two ideas

**Duplication — but only the essential kind.** Two or more near-identical passages are a standard extraction trigger. The trap: don't unify code that merely *looks* alike for accidental reasons. A helper that computed an address and was reused three times got a name; a fourth, superficially similar use case later needed a different final step, and rather than force it through the existing name with a parameter, the right move was recognizing the fragment had two purposes wearing one name and splitting it at a finer grain. Check: does the piece you're about to extract serve one purpose, or does it just currently look the same across sites that don't actually share intent? If a later caller needs to bolt a condition onto the shared piece to handle its case, that's the sign the earlier extraction was coincidental, not essential.

**A boolean or mode parameter that selects behavior.** Trigger: a function takes a flag and branches internally on it to decide which of two things to do. What goes wrong: you've asked the running program to make a decision you already knew the answer to at the call site, and the flag's meaning ("true bletches" vs. "false bletches") rarely matches how anyone thinks about the problem. What to do: split into two named operations, one per behavior, and factor out only what's genuinely common between them. How to check: do the names of the two call sites read as sentences, or do they read as "true, x" / "false, x"?

**Nested prerequisite checks, or a chain of if/else-if on one discriminant.** A validation pipeline nested four checks deep forces a reader to count nesting depth to find out when the final action fires. A sequence of "if button A, else if button B, else if button C" pays a decision cost on every call even though the input already determines the outcome, and every new case means editing the chain. What to do: give each check its own named unit with local failure handling, so the top level reads as a flat list of named steps; replace sequential dispatch with routing keyed directly on the discriminant (a lookup rather than a chain). How to check: does adding a new case mean inserting a branch into existing code, or adding one independent entry? The latter means the dispatch is factored correctly.

**You need a comment to explain what a variable still means, or you've nested a loop inside a loop.** Both are complexity outrunning what a reader can hold in mind at once (a working-memory ceiling of roughly seven items shows up repeatedly as the practical size limit for one function). Trigger: you feel the need to remind yourself, in a comment, what a value still represents partway through a function — or you find a loop body that itself contains a loop doing something independently meaningful. What to do: factor at exactly that point; the extracted piece replaces both the comment and the need for one. How to check: could you delete the explanatory comment because the code it was explaining is now a named call instead of inline reasoning?

**Names that are concatenations, or that have numbers baked in.** `enable-left-motor` / `disable-right-solenoid` is a cross product of two independent concepts (an action, a target) glued into one identifier per combination; `1channel`, `2channel`, `3channel` is a piece of data (which channel) smuggled into an identifier instead of passed as an argument. Both are decomposition failures disguised as naming ones — see Section 5.

## 4. Signals you've factored too far

This direction gets equal weight deliberately: the same book that argues for aggressive factoring is unusually blunt about factoring being a cost, not a virtue.

**Wait for real repetition before generalizing.** With one instance of something, you don't know whether a general solution is even warranted. With two, it's marginal. With three, the shared shape becomes visible enough to justify pulling out a general mechanism — and even then, expect real instances to differ enough that a single "universal" structure ends up wrong anyway, because the more complex the underlying need, the less likely any one structure covers all of it. Trigger: you're about to build a generic/configurable mechanism for a need you have exactly one concrete case of. What to do: write the concrete case; write the general shape only once you have two or three real, divergent examples to generalize *from*, not one imagined example to generalize *toward*. How to check: can you point to actual second and third callers, or are they hypothetical?

**Defer the restructuring you already know is coming.** It's normal to notice, mid-implementation, that two concerns are tangled in a way you know should eventually be split — and still choose not to split them yet, because the correct shape of the split isn't knowable until more of the system exists. The point isn't laziness; it's that restructuring based on a partial picture usually guesses wrong and has to be redone anyway. What to do: get the current iteration working, and prepare for the anticipated future change by organizing information cleanly (clear naming, honest boundaries around what exists today) rather than by pre-building the mechanism (hooks, flags, generic layers) the future change might need. Add complexity only when the iteration in front of you requires it.

**Don't factor for factoring's sake.** A commonly recurring short phrase is a tempting extraction candidate, but naming it can make code *harder* to read if the raw phrase is already more transparent than any name you can invent for it, and if it turns out to be used only once anyway. Good factoring sometimes reduces the number of names in a system rather than growing it — collapsing several near-duplicate named things into one thing parameterized by what actually varies is itself evidence the factoring was right; a rising name count is not automatically progress.

**Check whether the spec's complexity is real.** Given two solutions that both meet the requirement, prefer the simpler one — not as a stylistic tiebreaker but because it's easier to verify, debug, and change, and added complexity has to be justified by something, not assumed harmless. Before building machinery to match a requirement that looks combinatorially complex, ask whether the complexity describes the actual problem or is inherited from someone's *prior, different* solution being redescribed as if it were the requirement itself. A spec built around a legacy implementation's shape (separate hand-tuned terms mirroring old analog components, say) can collapse dramatically once you re-derive from what's actually needed instead of encoding what was asked for literally.

**Don't build a private interpreter to buy flexibility your language already gives you for free.** The urge to make something "configurable" or "data-driven" by inventing a small command language or plugin layer rarely reflects something genuinely unique about the problem — it reflects the mechanism being fun to build. Once built, the interpreter becomes the largest, least-tested, least-used part of the system, and you've quietly changed jobs from solving the problem to maintaining a runtime. Check: is there something about this problem that a plain function or module genuinely can't express, or are you enjoying building the indirection?

**Don't bury your tools.** An abstraction that exposes only a fixed menu of finished, "safe" operations — deliberately hiding the primitives it's built from — looks clean until a caller needs a composition the designer didn't anticipate (a hardware layer offering sixteen canned commands but no way to do fast bulk output, forcing every caller who needed that to bypass the abstraction entirely). Expose the composable primitives alongside the convenience operations; an abstraction that can only be used exactly as its author imagined will be worked around, not respected.

## 5. Naming as a correctness check

**If you can't give it one non-compound name, it isn't a well-formed concept yet.** This is the sharpest naming rule and it runs in both directions: struggling to name a factored-out piece is not a vocabulary problem to push through, it's feedback that the boundary itself is wrong. Trigger: you keep reaching for an adequate-but-not-quite-right name across several attempts. What goes wrong: shipping the mediocre name lets the fuzzy concept survive, and the fuzziness resurfaces later as awkward call sites built around a thing nobody can quite describe. What to do: treat the difficulty as a prompt to re-examine what the chunk actually *is* — often a workaround name is standing in for a real, distinct concept nobody has recognized yet — before settling.

**Name by effect, never by mechanism.** A name should describe what a piece accomplishes for its caller, not how it's implemented internally. Check: could the internals be rewritten completely without the name becoming a lie? If changing the implementation would make the name inaccurate, the name described the mechanism, not the purpose.

**Read the call site as a sentence.** Names are chosen with the phrase they'll form at their use sites in mind, not in isolation. If a call site doesn't parse as a natural phrase describing an action, the boundary underneath it is probably drawn in the wrong place, not just labeled wrong. This is the same test that catches the hyphenated/hardcoded-number smells from Section 3: the growth rate of names you need as you add variants is itself evidence for or against a boundary — factoring that collapses combinations into composable parts, rather than enumerating them, is the one that scales.

## 6. Where state lives

**Prefer explicit parameters over ambient state, and default to the narrowest scope.** A unit that reads or writes something outside its own parameters can't be tested or reused in isolation, and can't be verified without recreating whatever ambient context it silently depends on. Trigger: introducing a new piece of state. What to do: default it to the smallest scope that can hold it — local to one routine — and widen it only once a second, genuinely independent component needs to read or set it too. Check: can you call this twice in a row, in isolation, and get consistent results?

**Set state correctly at the start of an operation rather than saving and restoring it at the end.** Save-then-restore looks tidy but breaks under any non-local exit — an early return, an error, an abort skips the restore and leaves corrupted ambient state for something else, elsewhere, to trip over later. What to do: where possible, have an operation establish the state it needs explicitly rather than mutate shared state and promise to put it back. If restoration genuinely can't be avoided, centralize it in one routine invoked at every real exit path rather than duplicating the restore logic per path.

**When you're about to wrap an ambient-state routine with save/restore to get a parameterized variant, invert it instead.** If you already have a routine that operates on some shared value, and you now need a version that operates on an arbitrary value without disturbing the shared one, don't build the new version as a save/restore wrapper around the old one. Extract the core behavior to take the value as an explicit parameter, then rebuild the original ambient-state convenience version as a thin call into the now-parameterized core. This removes the fragile save/restore step entirely rather than adding a second layer of it.

**Two independent uses of one shared flag or resource are safe only under two conditions: they never overlap in time, and each restores prior state on its way out.** If either can't be guaranteed — the two uses can nest — a single boolean toggle will have one use's cleanup clobber the other's still-active state. What to do: either give the second concern its own independent state, or replace a boolean with a nesting counter so overlapping activations compose instead of colliding, guarding against the counter going negative on an unpaired call.

**Values that are always read or written together as a group are one concept, not several variables.** If you find yourself repeatedly saving, restoring, or swapping the same cluster of values as a unit, merge them into a single addressable structure so the whole group moves atomically — saving five of six independent variables, or restoring them out of order, is a failure mode a grouped structure eliminates by construction.

## 7. Control structures as a design diagnostic

**Treat every conditional as a question, not a neutral tool.** The default assumption should be that most apparent decisions in a system are not genuine branches at all but dispatch — the input already determines the outcome, and the honest implementation is to route directly to it rather than test for it. Trigger: writing an `if`. Check: does this branch encode two genuinely different processes, or does it just select between two values or two names for the same process? The latter almost never needs to be a branch.

**Two branches differing only in which number comes out should be computed, not decided.** If both arms of a conditional produce a different value rather than doing different work, derive the result from the condition arithmetically — a boolean is already a 0/1, and a small lookup or a direct calculation replaces the branch entirely. The caution attached to this move matters as much as the move itself: this is a legitimate technique only when it leans on an assumption that's genuinely stable and either well-known or explicitly documented at the point of use; applied to something likely to change, or left unexplained, the same trick becomes a trap for the next reader. And when the underlying decision is genuinely trivial, the "clever" arithmetic rewrite sometimes isn't worth it even when it's shorter — a plain conditional that matches how a reader thinks about the problem can beat a denser one that doesn't.

**A cluster of hand-tuned special cases patched around the edges of one model is a symptom, not a set of bugs to fix individually.** Three regimes with empirically adjusted transition thresholds, each getting its own conditional and its own edge-case fixes over time, means every patch treats a symptom. The higher-leverage move is to ask whether a single reformulation removes the need for discrete regimes at all, rather than continuing to tune the boundaries between them.

**A check that guards against a state the caller already structurally guarantees can't occur is defensive weight, not robustness.** If you can point to the exact upstream place that already makes a condition impossible, a downstream re-check of the same condition just dilutes the signal of the checks that matter. Push the guarantee to where it's actually established and trust it below that point; more aggressively, look for a representation where the "special case" simply becomes a normal case that needs no check at all.

## 8. The iterative loop

**Neither big-design-up-front nor no-design-at-all survives contact with a real project.** Attempting to plan nearly everything before writing code fails because requirements are genuinely not fully known until users react to something running, not to a document. Skipping design and writing code immediately fails differently: the system becomes unmaintainable within a couple of years because no record exists of *why* the boundaries are where they are — not even to the people who drew them. The workable middle is building just enough of a conceptual model to know the shape of the problem, then switching into a tight, repeating loop of implement-a-slice → test it against the requirement → revise, at whatever grain size fits (a subsystem, or a single function).

**Build throwaway prototypes under an explicit rule that none of the code survives.** This removes the pull to freeze an interface or a boundary decision purely because it's already written and working. Teams that let a prototype's code quietly become the final version consistently end up with worse boundaries than teams that treat the prototype as disposable and rebuild once the shape is understood.

**Work on one dimension of a problem at a time, and change as little as possible between test cycles.** Get the primary behavior working before adding the variation that changes it (draw a shape before adding erase-the-shape as a variant), and resist bundling several unrelated fixes into one edit-compile cycle. Both are the same discipline: when something breaks, you want to know unambiguously which change broke it.

**Estimate cost by summing the smallest real pieces, not by gut-feel on the whole.** A change that feels trivial as a single lump reliably costs several times a naive estimate once redesign, retesting, and documentation across every actually-touched piece are counted. Leaving a task undecomposed in your head produces bad judgment about its size, independent of whether the resulting code is any good.
